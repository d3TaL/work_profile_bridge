# Промпт для агента

Ты разрабатываешь Profile Link Bridge — Android-приложение на Kotlin для открытия поддерживаемых ссылок внутри выбранного рабочего профиля или Samsung Secure Folder. Ozon и банковские приложения — целевые обработчики. Один APK устанавливается в несколько пространств. Главный телефон владельца, по его словам: Android 17 / One UI 9; парк Android 11–17, One UI 8.5/9. Не считать эти конфигурации уже протестированными.

Найди этот комплект в корне проекта либо в `agent-handoff`. Прочитай его AGENTS.md, docs/PROJECT_STATE.md, docs/DIAGNOSTICS.md, docs/SECURITY.md и docs/IMPLEMENTATION_PLAN.md вместе с действующими инструкциями репозитория. Используй доступные Kotlin/Android skills: прочитай их инструкции, укажи фактически использованные skills. Для системных ограничений используй официальные Android/Samsung документы.

Текущая проблема: в рабочем профиле TLS-тест завершается одинаковым сообщением «TLS-проверка не прошла, соединение остановлено без перехода на незащищённый канал» в обе стороны. В Secure Folder ранее внешняя копия сообщала «Получатель недоступен»; успешный TLS не подтверждён ни в одном направлении. Пользователь переключался через многозадачность. Проверка Secure Folder с обеими копиями на экране не выполнена. Не проси снова многократно повторять тот же тест без новой диагностической информации.

Твоя первая задача — сделать проверяемую диагностическую сборку, затем двигаться к полноценному приложению:

1. Инвентаризируй реальный код, инструкции, зависимости и возможности среды. Найди TlsProbe, TlsContexts, AndroidTlsIdentity, ProbeViewModel и отображение ошибок либо их аналоги. Не предполагай наличие файлов по названию из переписки.
2. Если исходники 0.1.1 есть, продолжи их без полной перезаписи. Если их нет, явно создай новую минимальную реализацию диагностического этапа с тем же назначением; не выдавай её за восстановленный побайтово проект. Укажи последствия новой подписи. Не блокируй работу из-за отсутствия старого архива, если доступно создание новой реализации.
3. Введи структурированную диагностику на обоих концах: identity/key, TLS context, bind/listen, TCP connect/accept, handshake, certificate/pin validation, fixed ping/ACK, stop/expiry/cancellation. Сохраняй различие между наблюдаемой причиной и предположением. Если провайдер не даёт отличить причину, покажи UNKNOWN, а не выдуманную причину.
4. Добавь локальную self-check проверку внутри одного профиля с отдельным тестовым соединением, не снимая защиту pin. Она должна отличать проблему AndroidKeyStore/Conscrypt от недоступности границы профиля. Не удаляй пользовательскую identity и не ослабляй доверие для теста.
5. Сделай безопасный просмотр/экспорт отчёта без URL, кодов сессий, токенов и ключей; срок сессии и состояние listener должны быть видны. Используй docs/DIAGNOSTICS.md как критерии.
6. Запусти подходящие тесты, lint и сборку. Если SDK/сеть недоступны, всё равно подготовь код и инструкции, а невыполненные проверки перечисли честно. Не меняй TLS/verification настройки ради обхода ошибок среды.
7. Дай debug APK, SHA-256, changelog, инструкции одного короткого эксперимента на рабочем профиле и шаблон отчёта. Производственные ключи не создавать и не заменять молча. Попроси только новые данные, которые действительно нужны после правки.
8. После получения отчёта выбери разрешённый транспорт. Android 17 запрещает межпрофильный localhost по умолчанию независимо от targetSdk. Для work profile исследуй CrossProfileApps и разрешённые DPC intent filters; эти API не дают автоматически права запускать любой пакет. Для Secure Folder сначала докажи наличие поддерживаемого пути. Если его нет, оформи явное ограничение продукта. Успех одного направления, если он когда-либо будет подтверждён, ещё не означает готовность обратного канала или фоновой доставки.
9. Затем реализуй сопряжение/отзыв, проверку политики получателя, URL routing, TTL и дедупликацию, состояния доставки и пользовательское открытие. Не передавай банковские URL через диагностический протокол. Автоматическое повторение после UNKNOWN_OUTCOME запрещено.

Работай до конкретного проверяемого результата; не ограничивайся рекомендациями. Не заявляй, что весь продукт готов после диагностической сборки. В первой итерации готовый результат — код диагностики, автоматические проверки, собранный APK при доступной среде и точный сценарий проверки. Последующие этапы могут зависеть от отчёта с физического устройства.

Не отключай certificate validation/pinning, не добавляй незашифрованный fallback, root, обход блокировки Knox или скрытые API. Не предлагай бессрочный фоновый сервис до доказательства транспорта и проверки допустимого режима Android. Держи URL и секреты вне логов/backup; I/O вне main thread; сокеты закрываются при отмене.

Отчёт пиши по-русски. Заверши перечислением изменённых файлов, фактических проверок, пути к APK и контрольной суммы, ограничений и одного следующего шага. Сохрани состояние работы в git и docs/VALIDATION.md, чтобы следующий агент мог продолжить без истории чата.
