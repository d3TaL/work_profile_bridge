# Безопасность

## Активы и недоверенные источники

Защищать банковские URL с одноразовыми токенами, правила назначения, peer credentials и ключи. Недоверенные: вызывающее приложение, URI/Intent, любое локальное приложение, процесс на том же localhost, импортированный код пары и другой экземпляр без подтверждённого доверия. Доверие к DPC/OEM не даёт нашему приложению неограниченные полномочия.

| Риск | Требование |
| --- | --- |
| Ложный local listener | TLS peer authentication; localhost не является идентичностью |
| Подмена pairing code | Подтверждённый перенос/сравнение, срок, отзыв; не silent TOFU |
| Downgrade/MitM | Штатный TLS, обязательный pin/доверие, отсутствие plaintext fallback |
| Replay/duplicate | Message ID, TTL, bounded replay store и определённое поведение после reboot |
| Intent injection | Новый минимальный Intent после независимой валидации, без чужих flags/extras/grants |
| URL confusion | Точное доменное правило с dot boundary, raw URL сохраняется, неоднозначность требует выбора |
| Утечки | Нет секретов в логах, saved state, backup, crash analytics и отчётах |
| Фоновый запуск | Пользовательское подтверждение/уведомление по правилам ОС; не обход BAL |
| Переполнение/DoS | Ограничения frame/URL/очереди, TTL, timeouts, число соединений, bounded buffers |
| Supply chain | Fixed versions, wrapper checksum, verification metadata, locks, pinned CI actions |

## TLS и ключи

Сохранить TLS 1.3 diagnostic contract прежней версии, если код продолжает её; любое изменение протокола обосновать отдельно. Android 11+ предоставляет подходящие TLS API, но совместимость AndroidKeyStore opaque key с конкретным провайдером доказывается тестом на устройстве. Нельзя выдавать успешный JDK тест за такую проверку.

Не подставлять экспортированный private key, тестовый PKCS12 или TrustAll как «исправление». Фикстура с заведомо синтетическим private key допускается только в test resources и не попадает в APK. Ключ подписи APK, TLS identity и ключ шифрования хранения — разные сущности.

Временный PLB2 pin+token — только диагностика. Для production pairing спроектировать взаимное подтверждение и идентичность обеих сторон, отдельные scoped credentials, key rotation, отзыв, reinstall/reset и UX. Рассмотреть mTLS или другой проверенный аутентифицированный протокол; не изобретать криптографию и не обещать mTLS до реализации.

## URL и запуск

Диагностический лимит прежнего parser был 16 KiB; зафиксировать, считаются байты или UTF-16 code units. Для протокола проверять размер UTF-8 до выделения/отправки frame. Отвергать управляющие символы, userinfo, неожиданные порты/схемы и неоднозначное представление host согласно документированной политике. Query/fragment не переписывать, не сортировать и не декодировать повторно: подписи банковских ссылок могут зависеть от исходной строки.

Маршрут сопоставляет разрешённый host/path с выбранным пакетом, а не произвольным Intent из сети. При одинаково подходящих правилах — выбор пользователя. Независимо проверить разрешение receiver-side, наличие экспортированного обработчика и lifecycle непосредственно перед новым package-scoped ACTION_VIEW. Открытие приложения не равно подтверждённой банковской операции.

## Разрешения и данные

Минимальный manifest, exported только для нужных entry points. Никаких QUERY_ALL_PACKAGES и широких storage permissions без доказанной необходимости. Управление профилем и разрешённые intent filters не предполагать доступными обычному APK. Для резервного копирования/переноса явно исключить секреты; настройку проверять на поддерживаемых версиях Android. Не требовать ACCESS_LOCAL_NETWORK ради «разблокировки» границы профилей без документированного основания.

Для production persistence выбрать поддерживаемые актуальные API, AndroidKeyStore-backed encryption для credentials и защиту от восстановления без ключа. Не добавлять устаревшую security-библиотеку по привычке. Очередь ссылок по умолчанию в памяти; дисковая очередь — отдельное решение с threat model.
