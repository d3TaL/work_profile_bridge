# Инструкции агенту разработки

## Цель

Разработать Kotlin Android APK для передачи выбранной поддерживаемой ссылки из основного профиля в рабочий профиль или Samsung Secure Folder и открытия её целевым приложением в выбранном пространстве. Ozon и банковские приложения — целевые сценарии. Один APK может иметь отдельные экземпляры в разных пространствах. Secure Folder не считать обычным managed work profile.

## Сначала прочитать

Прочитать существующие инструкции репозитория, затем PROJECT_STATE, DIAGNOSTICS, SECURITY и IMPLEMENTATION_PLAN из этого комплекта. Найти их относительно расположения этого файла. Сверить документы с реальным кодом и SDK. Предыдущие сообщения о сборке — исторические сведения, не результаты текущего checkout.

## Обязательные правила

1. Сначала устранить недостаток диагностических данных. В рабочем профиле TLS падает в обоих направлениях, точная причина не установлена. Не объявлять причиной Samsung, AndroidKeyStore, pin, фон или сетевой запрет без доказательств.
2. На Android 17 межпрофильный loopback запрещён по умолчанию независимо от targetSdk. Не строить основную архитектуру на предположении общего localhost. Понижение targetSdk, разрешение локальной сети и TLS не являются доказанным решением этой проблемы.
3. До изменения транспорта изучить публичные Android/Samsung API, требования разрешений и DPC. Не обещать поддержку Secure Folder при отсутствии разрешённого публичного канала.
4. Использовать применимые доступные Kotlin/Android skills. Найти и прочитать их SKILL.md; записать названия и версии/commit в отчёт. Если skill недоступен, честно отметить это и следовать официальной документации. Не утверждать, что skill применён только по ссылке на него.
5. Разработку вести в git, сохранять небольшие осмысленные изменения. Не удалять чужие изменения и не перезаписывать ключ подписи. При неизвестном ключе отличать новый debug APK от обновления старой установки.
6. Никаких TrustAll, разрешающего hostname verifier, plaintext fallback или отключения pin ради прохождения теста. Не добавлять root, Accessibility, overlay и скрытые Knox API для обхода изоляции.
7. Не передавать настоящие URL через диагностический ping. Диагностика, доверие к паре, доставка URL и запуск Activity — разные этапы.
8. Не логировать URL, query/fragment, коды сессий, токены, ключи и произвольные тексты исключений. Экспорт отчёта только по действию пользователя, с просмотром содержимого.
9. Входящие Intent недоверенные. Извлекать минимальные разрешённые поля, одинаково обрабатывать cold/warm launch. Не ретранслировать исходный Intent, extras, ClipData, flags или URI grants.
10. Ключи — AndroidKeyStore; не экспортировать private key. Проверить реальную совместимость ключа с TLS-провайдером на Android, не только JVM. Не обещать аппаратную защиту без проверки.
11. I/O, генерация ключей и тяжёлые PackageManager-запросы вне main thread. Structured concurrency, отмена и закрытие сокетов обязательны. Не использовать GlobalScope, busy polling и бесконечные повторы.
12. Не добавлять FGS с фиктивным типом. Обосновать законный режим фоновой работы по версии ОС. При недоступном контейнере — понятное состояние и ручное продолжение.
13. Не делать массовый upgrade зависимостей вместе с исправлением TLS. Проверить совместимость текущего Gradle/AGP/Kotlin/JDK; обновлять отдельно и по необходимости. Запретить динамические версии, сохранить wrapper checksum, locks и verification metadata.
14. Тестировать содержательные изменения. Не писать тесты ради покрытия строк; проверять границы доверия, отказ, отмену, жизненный цикл и неоднозначный результат запуска.
15. Не публиковать APK/репозиторий, не добавлять облачный relay и не менять DPC без отдельного поручения. Локальные сборки и исправления входят в задачу.
16. В конце каждой задачи: что изменено, что проверено фактически, что не проверено и почему, ограничения, точный APK/commit и следующий шаг. Нельзя выдавать компиляцию за доказанную совместимость телефона.

## Стиль кода

Kotlin, Android Jetpack, Compose Material 3, ViewModel и StateFlow с lifecycle-aware collection. Immutable state, sealed outcomes, явные зависимости и проверяемые интерфейсы. Не вводить модули, DI-фреймворк или БД без текущей необходимости. Версии и API выбирать по официальным актуальным источникам, а не по формулировке «самые новые».

Диагностическая ошибка должна быть моделью с этапом и безопасным кодом причины. Не сводить все IOException/IllegalArgumentException к одному сообщению. Не перехватывать CancellationException как сетевой отказ. Внешнему клиенту не раскрывать подробности, помогающие перебору доверия; диагностические подробности показывать локальному пользователю.
